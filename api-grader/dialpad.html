What this means for you.

One paragraph per category, in plain language.

1 · Functional Coverage

15 / 15 points

Dialpad's API exposes essentially the whole communications platform. You can read users and calls, send texts, place, transfer and end calls, provision and assign phone numbers, manage call routing, and subscribe to real-time events for calls, texts, contacts and agent status. For automations and AI agents built around phone and text workflows, the surface is broad and mature. The one gap: inbound texts arrive through event webhooks, because there is no message-history endpoint to read them back.

See technical details→

2 · Design & Reliability

5 / 10 points

The API is a clean, predictable REST interface, errors come back structured with a machine-readable reason, and uptime is public on a status page with its own API component. The weak spots are the reliability guarantees. There are no idempotency keys, so retrying a failed send can text someone twice. There is no concurrency control, so the last write wins. There is no documented rate-limit contract, with no 429, no Retry-After and no limit headers. And webhooks are signed but come with no documented retry or ordering promise. Plan to build your own dedup, backoff and webhook reconciliation.

See technical details→

3 · Access Control

3.5 / 5 points

You can issue multiple named keys, scope them somewhat, set them to expire or revoke them yourself, and test in a separate sandbox with its own credentials. What you cannot do is mint a read-only key, so handing a limited key to an AI agent or a third party carries more risk than it should. A dedicated, narrowly scoped OAuth app and close monitoring are the workaround.

See technical details→

4 · Docs & AI-Ready

3.8 / 5 points

An AI coding tool can work with this API well: there is an OpenAPI file, a maintained official Python SDK, a first-party MCP server, an llms.txt index, and a Markdown version of every reference page. The reference has no copy-and-paste request examples, it documents none of the error responses your code will actually hit, and the public changelog has not been updated since July 2025.

See technical details→

5 · Access & Cost

11.3 / 15 points

Once you are on a plan that includes the API, getting a key is instant and self-serve: a company admin creates it in the product, with no sales call. The catch is the plan. API access is not on the cheapest tier, and Dialpad's own pages disagree on exactly which tier includes it, so confirm yours does before you build.

See technical details→

What works

  • Near-complete coverage of calls, texts, users, phone numbers, routing and contacts
  • Place, transfer and end calls and send texts straight from the API
  • Real-time event subscriptions for calls, texts, contacts and agent status
  • Structured errors with a machine-readable reason, confirmed live
  • A separate sandbox with its own credentials
  • Multiple named keys with expiry dates, and self-serve revocation
  • An OpenAPI file, a maintained Python SDK and a first-party MCP server
  • An llms.txt index and a Markdown version of every reference page
  • A public status page with a dedicated API component and published uptime
  • Self-serve keys created by your own admin, with no sales call

What to watch

  • No idempotency keys, so a retried text or call can go out twice
  • No concurrency control: the last write wins
  • No documented 429 or Retry-After, and no rate-limit headers on live responses
  • Webhooks are signed but have no documented retry or ordering guarantees
  • No read-only key, so every credential can act, not just look
  • Inbound texts come only through webhooks; there is no message-history endpoint
  • No changed-since sync; the bulk export covers call records only
  • Error responses work at runtime but are not documented anywhere
  • The public changelog has not been updated since July 2025
  • API access is not on the cheapest plan, and Dialpad's pages disagree on which tier includes it
  • Writes were graded from documentation, not tested live
